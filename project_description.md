# Detailed project description

The project is organised as a pipeline. `agent.py` coordinates `agent_core`; `dsh.py` provides model loading and Python execution. This document grows as each block is implemented.

## Block 0 — Orchestration

`Agent.solve(tasks)` coordinates the blocks below for each batch of up to eight tasks. It builds the prompts, calls the model, runs the generated Python programs, and validates their results.

It keeps a safety margin within the 40-second limit and reserves time for execution. It returns one numeric answer per task in the original order, with `0.0` for failed or unfinished tasks.

## Block 1 - Router

This is a small deterministic process implemented in `agent.py`.
By identifying keywords in the objective and checking for attached files, it applies the following rules:

1. A task without files is a calculation task.
2. A task with files that mentions fitting or regression is a fit task.
3. Every other task with files is a table task.

The function returns `"calc"`, `"fit"`, or `"table"`.

## Block 2 — Schema profiler

`build_data_card(objective, file_paths)` prepares a compact file context for the LLM. It preserves `data_dictionary.csv` unchanged. For each data file, it reports the name, dimensions, separator, decimal mark, physical column names, observed missing-value tokens, and the first three raw rows.

- We identify the separator with a helper: `_detect_separator`. It uses `csv.Sniffer`, with a header-frequency fallback.
- We detect the decimal format with a helper: `_detect_decimal_format`. It uses regular-expression matching (for example, `re.compile(r"^[+-]?\d+,\d+(?:\s*[^\d].*)?$")`) to identify decimal commas or points.
- We identify missing values by comparing every cell value with a hard-coded list of potential NaN placeholders. We also scan the objective for task-specific numeric missing-value placeholders, such as `-1`. This process uses regular-expression matching.

Its output is passed to the prompt builder.

## Block 3 — Prompt builder

`build_prompt(objective, route, data_card)` creates one compact LLM prompt, formatted as a conversation split between the `system` and `user` roles required by the model.

- The `system` content defines permanent rules: return executable Python code only, follow every objective instruction, and assign one finite numeric answer to `RESULT`. It also adds route-specific guidance: Python/SymPy/NumPy for `calc`, pandas for `table`, and pandas with scikit-learn for `fit`.
- The `user` content contains the task objective. For `table` and `fit` tasks, it also includes the data card produced by the schema profiler.

It returns two message dictionaries ready for `dsh.LLM.chat()`.

## Block 4 — LLM generation

`generate_programs(conversations, max_time)` sends the prepared conversations to `dsh.LLM.chat()`.

- We load the model selected in `config.py` once, when `Agent` is created.
- We generate replies in batches at temperature zero, with a configured token limit per reply and a shared time budget for the model call.

The function returns one reply per conversation in the original order. These replies provide the code for the executor.

## Block 5 — Executor

`execute_program(reply, file_paths, timeout_s=PROGRAM_TIMEOUT_S)` runs one Python program generated by the LLM. It takes the model's reply and the paths to the files attached to that task.

`Agent.solve()` uses a `ThreadPoolExecutor` to run up to `MAX_WORKERS` programs at a time, with three workers by default.

- We use `_strip_code_fence()` to remove a surrounding pair of triple backticks if the model wraps its code in Markdown.
- We pass the cleaned code and file paths to `dsh.run_python()`. It runs the code in a fresh Python subprocess with the task files available by filename. 

The function returns the `ExecResult` from `dsh.run_python()`. It includes the value assigned to `RESULT` on success or an error message on failure, along with captured output and execution time. This result is passed to the numeric validator in the next block.

## Block 6 — Numeric validator

`validate_result(result)` checks the `ExecResult` returned by the executor.

- We check whether execution succeeded and raise an error with the executor's message if it failed.
- We use `dsh.to_number()` to convert `RESULT` to a finite number. Values such as lists, booleans, and `NaN` raise an error.

The function returns the validated number. When validation raises an error, `solve()` keeps the fallback answer of `0.0` for that task.

## Block 7 — Local evaluation

`evaluate_dev.py` shuffles `dev.json` with a fixed seed and splits it into 80% tuning and 20% holdout, keeping a similar mix of `calc`, `table`, and `fit` tasks.

The evaluator checks answers against their tolerances and reports accuracy by task type, failed task IDs, model load time, and batch times. With `--model-log`, it saves the prompts and raw model replies in one timestamped JSON file.
